# 모니터링 플랫폼 감사와 수정 계획

> 구현은 아래 순서대로 진행한다. 단계마다 재현 테스트를 먼저 만들고, 해당 단계의 검증을 통과한 커밋을 남긴다.

**목표**는 GPU와 Storage의 기존 화면 및 운영 동작을 보존하면서, 이번 감사에서 확인한 데이터 손실, 수집 중단, 배포 경계 문제를 수정하는 것이다.

**구조**는 하나의 저장소에 GPU와 Storage의 독립 런타임과 릴리스를 유지한다. 각 문제는 상태나 데이터를 최초로 소유하는 모듈에서 고친다. 공통 CI는 두 앱의 패키징 및 검증 계약을 확인한다.

**기준 커밋**은 로컬 `refactor/monitoring-repo-cleanup`의 `aac8734`다. Git에 추적되는 426개 파일의 구성과 주요 실행 경로를 조사했다. 코드와 로컬 재현을 바탕으로 작성한 계획이며 운영 환경의 데이터와 배포 설정에는 쓰지 않았다.

## 감사 범위와 근거

| 영역 | 이번에 확인한 경로 | 검증의 한계 |
| --- | --- | --- |
| GPU 화면 | 대시보드 갱신과 공유 서버 스토어, System 집계, Power Flow 편집과 모니터 전환, Vite 빌드와 런타임 프록시 | 운영에서 등록·삭제·배선도 저장을 수행하는 대신 로컬 브라우저와 격리 API로 검증했다. |
| GPU 백엔드 | 서버 CRUD와 수집 시작, SSH 명령 수명, Power Flow 저장·버전 충돌, 시간·이력, 하드웨어 조회 | 장애 및 대용량 SSH 출력은 테스트 채널에서 검증한다. 실제 BMC의 정격 정보는 아직 확보하지 못했다. |
| Storage | 목록과 상세 캐시, 재스캔과 잡 상태, 파일 저장과 검증, 스캐너와 에이전트, 패키징 | 재현은 임시 파일시스템과 테스트 데이터에서 수행했다. 운영 스캔·재스캔과 파일 삭제는 검증 범위 밖이다. |
| CI·배포 | 변경 경로 분류, 워크플로 안전 계약, 빌더의 SHA·체크섬과 런타임 파일, 관리형·단독 설치 경계 | 기준 커밋의 패키지는 로컬에서 확인했다. GitHub CI 실행 및 운영 활성화는 별도 작업이다. |

독립 검토는 GPU, Storage, CI·배포 세 범위로 나눴다. 아래 표에서 **재현**은 로컬 실행으로 관찰한 문제이고, **소스 확인**은 코드 경로를 확인한 개선 항목이다.

- 추적된 Python 파일 116개를 구문 분석했고 셸 파일 14개에 `bash -n`을 실행했다.
- 저장소 Python 테스트 210개와 워크플로 정책 검사, GPU 백엔드 182개와 프런트엔드 403개 및 빌드가 통과했다.
- Storage Python 테스트 331개와 뷰어·배포·Linux 스캐너 검증이 통과했다.
- 기준 커밋의 두 패키지에서 메타데이터의 SHA, 아카이브 체크섬, 런타임 파일을 대조했다.
- 현재 검증에서 전체 운영 활성화 흐름과 GitHub의 실제 CI 실행은 수행 범위 밖이었다.

## 작업 순서

### 1. 설치와 테스트의 실행 경계

- [ ] `apps/storage-monitor/install.sh`에서 복사 전에 앱 설치 경로와 상위 경로를 검사한다. 관리형 링크를 만난 경우 대상과 외부 파일을 보존한다. README를 관리형 설치와 별도 단독 설치의 실제 진입점에 맞춘다.
- [ ] 임시 접두 디렉터리와 대상 sentinel로 일반 경로, 심볼릭 링크, dry-run을 각각 검증한다. 기존에 dry-run이 생성한 테스트용 파일 계약도 확인한다.
- [ ] GPU `backend/collectors/manager.py`의 자동 시작 경계에서 비활성화 플래그를 적용한다. 배치 시작과 서버 추가·수정 경로에 걸쳐 설정이 일관되게 작동하는지 테스트한다. 명시적인 연결 테스트는 기존 사용자 흐름에 맞춰 검증한다.
- [ ] 인메모리 CRUD와 가짜 수집기로 등록·수정·삭제의 반환값, 자동 시작 가능 횟수, 중지 상태를 검증한다. 이후 브라우저의 서버 관리 시나리오는 이 격리 조건을 사용한다.

### 2. 두 앱의 작업 종료와 복구

- [ ] GPU의 일반 SSH 수집에 실제 명령 종료 한계를 적용한다. 명령 승인, stdout과 stderr 읽기, 종료 상태 대기를 한 요청 수명 안에서 다룬다. 연결 오류와 정상 종료 코드 계약을 유지한다. 한 채널이 멈추면 해당 수집이 끝나고 다음 주기에 복구되는지 확인한다.
- [ ] `test_ssh_recovery.py`, 기존 `test_hardware_live.py`에 맞춰 큰 출력, 지연, 종료 실패, 기존 스토리지 측정값과 측정 시각 보존을 검증한다. 실제 서버에 접속하는 테스트 대신 종료를 통제할 수 있는 채널을 사용한다.
- [ ] Storage의 같은 호스트에 대한 잡 종료 쓰기와 폴링 쓰기를 조율한다. 일시 경합은 제한적으로 재시도하고 최종 상태 쓰기가 완료될 때까지 잡 소유권을 유지한다. 영구 쓰기 오류는 관측 가능하게 기록하고 재시작 시 복구를 검증한다. 기존 공개 저장소 API의 비차단 계약은 `collector/test_store.py:362–373`으로 확인한다.
- [ ] `collector/test_jobs.py`에서 잠금을 의도적으로 겹쳐 실행한 뒤 최종 상태가 저장되고 다음 재스캔이 가능해지는지 확인한다. 다른 호스트의 동시 실행과 실제 실패 기록도 확인한다.

### 3. 경로와 편집 초안 보존

- [ ] `scanner/hstscan.c`의 JSON 경로 직렬화가 유효한 UTF-8을 보존하도록 수정한다. 잘못된 바이트의 표시와 복사 가능 여부를 명시적으로 정한다. 기존 스냅샷은 현재 형식대로 읽고, 경로가 정상화된 결과는 새 스캔에서 받는다.
- [ ] 한글, 악센트 문자, 따옴표, 개행, 잘못된 UTF-8을 한 임시 트리에서 확인한다. `scanner/test_hstscan.sh`와 에이전트·뷰어 경로 검증에서 실제 파일명과 표시/복사 경로가 일치하는지 확인한다.
- [ ] Power Flow의 이동 보호 기준을 현재 보기 모드와 분리하고 초안 상태에 묶는다. 저장 후 이동, 이동 취소, 모니터링에서 편집으로 돌아오기, 브라우저 새로고침을 확인한다.
- [ ] 저장 충돌 409, 버전 이력, 배치안 복제를 기존 테스트와 브라우저에서 검증한다. 초안 변경과 복제 테스트에는 격리된 저장소나 가짜 HTTP 응답을 쓴다.

### 4. 화면과 서버 목록의 일관성

- [ ] Storage `viewer/app.js`에서 갱신된 목록에 남아 있는 서버만 기존 상세 스냅샷을 되살리도록 한다. 전체 갱신과 개요의 30초 상태 갱신이 같은 서버 소속 규칙을 적용하게 한다. 활성 서버 제거, 다른 서버를 보던 중 제거, 같은 ID 재등록 순서를 각각 검증한다.
- [ ] System에서 정상 전체 응답을 기준으로 서버 소속을 조정한다. 실패하거나 일부인 응답에는 빠진 서버를 임의로 제거하지 않는 규칙을 유지한다. 응답 대기 중 도착한 WebSocket 관측값은 유지한다.
- [ ] 브라우저에서 서버 제거가 System 카드 목록과 요약 합계에 함께 반영되는지 확인한다. GPU Main의 탭·카드 배치, System의 기간·부분 측정, Storage의 상세 탭·갱신 오류 표시를 같은 데이터로 전후 비교한다.

### 5. Storage 저장 파일 보존 정책

- [ ] `collector/store.py`에서 동일 상태의 반복 쓰기를 줄이고, 활성 manifest와 복구에 필요한 세대의 보존 규칙을 정한다. 세대 보존 개수와 정리는 동시 읽기와 장애 시 복구를 테스트한 뒤 결정한다.
- [ ] 별도 테스트에서 읽기와 쓰기 경합, 중간 장애, 덜 쓰인 manifest, 유효 세대 복구를 검증한다. 일정 횟수 쓴 뒤 파일 수 상한과 최신 읽기 결과를 함께 검사한다. 운영에서 쌓인 기존 파일의 정리는 이 코드 변경과 별도 작업으로 한다.

### 6. Storage 릴리스 계약과 재시작 판정

- [ ] CI 분류에 실제 패키지 입력을 반영하고, 활성화 필수 파일과 HTML·Python의 런타임 의존성을 검사한다. 아카이브에서 실제 서버와 뷰어 진입점을 로드하는 확인을 추가한다.
- [ ] 아카이브 해시는 전송 및 SHA 검증에 계속 사용한다. 재시작 판정은 검증된 런타임 경로·모드·파일 내용으로 계산한 별도 해시를 사용한다. 이전 활성 상태에 런타임 해시가 없을 때의 최초 전환과 롤백 기록도 테스트한다.
- [ ] 실제 빌더로 문서 전용 변경, 빈 커밋, Storage 런타임·모드 변경을 각각 만든다. 가짜 활성화 명령을 연결해 동일 런타임은 활성화 호출 0회, 실제 런타임 변경은 1회인지 확인한다. 필수 파일이 빠진 아카이브는 활성화 전에 거부되는지 확인한다.

### 7. 검증 재현성

- [ ] GPU Python의 CI 설치와 런타임 설치가 같은 고정 해석 결과를 사용하도록 바꾼다. 기존 지원 Python과 실제 배포 플랫폼의 새 환경에서 설치 및 임포트가 되는지 확인한다. 변경 전후 설치 목록을 비교한다.
- [ ] 테스트 환경이 안전해진 뒤 핵심 브라우저 재현을 저장소에서 다시 실행할 수 있게 한다. 첫 묶음은 HTTP·WebSocket 순서 역전, Power Flow 초안 이동, Storage 서버 전환과 재스캔으로 제한한다.

## 유지할 계약과 운영 후속 확인

- GPU와 Storage는 독립 아카이브와 활성화 경로를 계속 사용한다. 로컬 감사 결과는 운영 반영 권한이나 성공을 뜻하지 않는다.
- Storage 수정 사항을 운영 반영하기 전에 1단계 설치 경계와 6단계 활성화 계약을 검증한다. 기존 활성 릴리스의 롤백 경로를 각 단계에서 확인한다.
- 썸네일이나 픽셀 비교는 동일 데이터와 화면 크기에서 수행한다. GPU 카드 좌표·문구·탭 동작, Storage 화면·캐시를 비교하고, 픽셀 오차는 동일 버전을 반복 캡처한 결과와 대조한다.
- 운영 GPU 대시보드, System, Power Flow는 로컬 HTTP 200을 반환했다. 하드웨어 API는 라이브 스냅샷 7개와 정격 정보 0개를 보고했다. PSU 부하율 활성화에는 실제 슬롯별 정격 정보가 필요하다. NAS 전용 NIC 구분이 필요하면 서버별 실제 링크와 IP를 확인한 뒤 별도 기능으로 다룬다.
- Storage 중앙 API의 인증 없는 서버 목록 요청은 401이었다. 서비스 유닛이 활성 상태인 것과 실제 클라이언트 경로에서 인증·대시보드가 동작하는 것은 별도 검증이다.
